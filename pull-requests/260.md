## Description

## Scope

This PR is intentionally based on restored stable `91658cc4` and changes only session/browser-auth safety. It does **not** port later category/filter behavior or offer/negotiation feature changes.

## Confirmed failure paths in 91658cc4

1. A stuck/slow `/session-refresh` could trigger a clean-session recovery that cleared cookies, localStorage and sessionStorage.
2. Login could treat the mere absence of known login controls as proof of authentication.
3. The pre-job checkpoint saved `bot-X.json` immediately after login returned, without a second strong-auth guard.
4. On an unsafe job ending, code restored `last-known-good`, which is actually the session from *before* the fresh pre-job checkpoint and can contain older auth tokens.
5. Headless mode blocked Vinted service workers by default.
6. Price-probe execution could share the production session context.
7. Two independently launched Playwright JVMs could write the same session files concurrently.

## Fix

- Never clear cookies/storage or invalidate persisted state because session-refresh/navigation is merely slow.
- Require visible conversations/inbox evidence before treating login as authenticated and before replacing `bot-X.json`.
- Give a restored session a bounded ~8s UI settle window before interactive login.
- Keep the fresh authenticated pre-job checkpoint if a job fails or finishes on an unsafe auth page; do not roll back to the older rotating backup.
- Keep service workers enabled by default; explicit env override can still block them.
- Isolate PRICE_PROBE from production session restore/persistence.
- Fail closed when production storageState cannot be restored.
- Add an OS-level runtime lock for the shared session directory.
- Add regression tests for refresh preservation, strong auth evidence, restored-session settling, checkpoint retention, service-worker default and duplicate runtime ownership.

## Session files

Active sessions remain `sessions/bot-X.json`. `.bot-*.json.tmp` files are staging files and stale ones are cleaned on startup. `sessions/backups` remains a recovery safety net and should not be manually deleted during normal operation.
