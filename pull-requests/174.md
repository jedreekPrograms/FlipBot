## Description

## Problem
Recent production logs show two regressions after the publication-time backfill/session hardening work:

1. every successful scheduled job creates a new timestamped `last-known-good` session backup, so `playwright/sessions/backups` grows extremely quickly;
2. the market observer can fetch many listing detail pages in a tight concurrent loop while normal bots are active. The same log window shows normal bots hitting Vinted rate-limit/session-block pages (`access to this site is blocked for this computer`). Incomplete baselines could also trigger another heavy recovery pass before the normal cooldown elapsed.

## Changes
- rotate `last-known-good` and `recovery` backups to one file of each type per bot instead of accumulating timestamped copies
- keep the active `bot-X.json` authoritative and preserve all existing fail-closed validation
- resolve market publication details sequentially with 1s spacing instead of concurrent `Promise.all` workers
- stop publication-detail work immediately on HTTP 403/429 or a Vinted block page
- abort the whole market-observer pass on that traffic-backoff signal instead of continuing through the remaining models
- always honor the configured market-stats cooldown; incomplete baselines no longer bypass it on the next 60s poll
- use a 30-minute failure/rate-limit backoff for the observer

## Scope
No change to normal bot job cadence, negotiation policy, offer limits, session restore source, mobile connectivity, or backend business rules. Normal bot browser contexts were already isolated per job before this PR; this change does not increase their creation frequency.

## Tests
- session tests cover rotating last-known-good/recovery backups
- publication resolver script test verifies sequential pacing and 403/429 backoff detection
