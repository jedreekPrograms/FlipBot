## Description

## Cel

Dodaje trwałą, backendową blokadę realnych akcji przed włączeniem scheduled real offers / next steps.

Problem, który rozwiązujemy: jeżeli Playwright wykona realny klik, a proces lub połączenie padnie zanim stan zostanie jednoznacznie zapisany w backendzie, kolejny scheduler run nie może bezwarunkowo powtórzyć tej samej akcji.

## Backend

### V16 `real_action_guard`
Nowa tabela przechowuje maksymalnie jeden aktywny guard na listing:
- `listing_id` UNIQUE + FK ON DELETE CASCADE
- `request_id` UUID UNIQUE
- `action_type`: `FIRST_OFFER` / `NEXT_STEP`
- `step_number`
- `created_at`

### Atomowe acquire
`POST /api/bots/{botId}/listings/{listingId}/real-action-guard/acquire`

- listing jest blokowany `PESSIMISTIC_WRITE`
- dwa równoległe procesy nie mogą dostać guardu dla tego samego listingu
- `requestId` generuje klient; ponowienie dokładnie tego samego requestu jest idempotentne
- replay jest fail-closed: jeżeli stan listingu już potwierdza wykonanie akcji, guard jest usuwany jako stale, ale acquire NIE zostaje ponownie przyznane
- inny aktywny guard blokuje kolejną realną akcję

### Release
`POST /api/bots/{botId}/listings/{listingId}/real-action-guard/release`

- zwolnić guard może tylko matching `requestId`
- brak guardu jest obsługiwany idempotentnie

### Walidacja stanu
- `FIRST_OFFER`: tylko `DISCOVERED`, step 1
- `NEXT_STEP`: tylko `NEGOTIATING`, dokładnie `currentStep + 1`
- confirmed stale guard może zostać automatycznie rozpoznany po stanie `NEGOTIATING/currentStep`

## Playwright

Dodany `RealActionGuardClient` + DTO dla acquire/release.

Ten PR **nie podłącza jeszcze guardu do realnego submitu**. Celowo rozdzielamy:
1. trwały mechanizm backend/API,
2. wiring pierwszej oferty,
3. wiring kolejnego kroku,
4. dopiero potem kontrolowane włączenie real actions.
