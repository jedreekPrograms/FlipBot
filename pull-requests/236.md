## Description

The current runtime fixes catalog concurrency at three even when CPU/RAM have headroom, while negotiations and the observer can allocate browsers outside that catalog cap. Jobs also wait for absent consent banners and repeat listing reads, and dashboard/history endpoints hydrate unnecessary entity graphs.

This change adds a process-wide adaptive browser admission budget for scheduled bots and the observer. It starts at three, spaces launches, reserves startup memory and grows after sustained headroom, up to the configured ceiling (logical CPUs, capped at 16 by default). Memory/CPU pressure defers new work without recording a job failure; marketplace backoff reduces the target and pauses growth. Running jobs finish and permits survive through browser cleanup. Existing per-account intervals, quotas, session-block cooldowns, session preview and last-known-good persistence remain in place.

It also removes the absent-cookie wait, shares negotiation listing reads within a job, uses lightweight bot/history/purchase projections and SQL counters, and serializes Bots-page polling with bulk runtime reads and cancellation of obsolete refreshes.

Rebased onto current stable 91658cc, preserving PR #235's human-verification changes unchanged. No schema migration is required. docs/performance-runtime.md describes Windows settings and the compatibility switch.

Validation: frontend lint and production build pass locally (one pre-existing hook warning). Added resource-admission/concurrency, cookie and snapshot tests plus PostgreSQL integration checks for history visibility, money rounding, periods, observer exclusion and zero entity hydration in the new read paths. Full CI is required before merging. Actual throughput and RAM on the user's Windows laptop have not been benchmarked; higher concurrency cannot guarantee absence of marketplace restrictions.
