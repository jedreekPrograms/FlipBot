## Description

## Problem

Nowe logi po PR #14 pokazują, że objaw „dziesiątek tysięcy kart” nie koreluje z żadnym eventem popup guarda: nie ma `POPUP STORM`, `Closing unexpected browser page` ani innych logów dodatkowych `Page`. Za to ten sam bot migruje między różnymi worker slotami, a każdy nowy slot odpala własny headful Chrome:

- bot 4 `NEGOTIATION_CHECK` -> slot 2
- bot 4 `CATALOG_SCAN` -> slot 3
- kolejny `NEGOTIATION_CHECK` -> slot 5

Przy małej liczbie RUNNING botów scheduler mógł więc stopniowo „obudzić” kolejne sloty/Chrome, mimo że nie były potrzebne. Dodatkowo scheduler używał `headless=false`, więc każde uruchomienie było widocznym oknem Chrome.

## Zmiany

### Scheduler headless by default
- `BrowserFactory` obsługuje jawny parametr `headless`
- `BrowserManager()` pozostaje headful dla legacy/manual `TestApplication`
- `BrowserManager(boolean headless)` jest używany przez scheduler
- nowy env `FLIPBOT_SCHEDULER_HEADLESS`
- default: `true`
- do debugowania można ustawić `FLIPBOT_SCHEDULER_HEADLESS=false`

### Dynamic worker slot startup
- `WorkerManager.start()` nie uruchamia już wszystkich slotów od razu
- pierwszy scheduler sync pobiera liczbę RUNNING botów
- uruchamiane jest tylko `min(RUNNING, FLIPBOT_WORKER_COUNT)` slotów
- jeśli liczba RUNNING botów później wzrośnie, kolejne sloty są dokładane do limitu
- sloty nie są agresywnie skalowane w dół podczas działania, co unika przerywania aktywnych jobów
- przy 2 RUNNING botach aktywne będą maksymalnie 2 sloty zamiast 10

### Thread safety
- każdy `BrowserManager` nadal jest tworzony i używany wyłącznie na owner thread danego slotu
- nie ma współdzielenia jednego Playwright/Browser między threadami

## Safety

PR nie zmienia:
- `FilterActions` ani text blocków
- popup guarda z PR #14
- negocjacji
- quota
- target matchingu
- DelayQueue / scheduling semantics
- real-offer flags

Scheduled real offers i next steps pozostają wyłączone.

## Jak testować

Uruchom `FlipBotPlaywrightApplication` z 2 RUNNING botami.

Domyślnie:
- nie powinny pojawić się żadne widoczne Chrome windows, bo scheduler działa headless
- log powinien pokazać `scheduler headless=true`
- po pierwszym syncu powinny wystartować tylko sloty 1 i 2
- log `activeSlots=2, maxSlots=10`
- kolejne joby obu botów powinny krążyć wyłącznie między tymi dwoma aktywnymi slotami, więc nie powinny uruchamiać slotów 3..10

Do ręcznej obserwacji UI ustaw przed uruchomieniem:
`FLIPBOT_SCHEDULER_HEADLESS=false`

Wtedy nadal powinny istnieć tylko 2 widoczne browser runtimes przy 2 RUNNING botach.
