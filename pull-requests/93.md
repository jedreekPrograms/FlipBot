## Description

Stage 12 hardens the backend listing state that persistent real-action guard/audit reconciliation uses as proof of completed marketplace actions.

Finding:
- `ListingService.updateListing()` historically loaded without the existing pessimistic row lock and accepted arbitrary `currentStep` changes together with status updates;
- real-action guard/audit reconciliation intentionally treats persisted `currentStep` as evidence that FIRST_OFFER / NEXT_STEP already happened;
- therefore the generic update endpoint must not be able to skip, rewind, or rewrite negotiation steps outside the actual sequential lifecycle.

Fix:
- updateListing now uses the existing `findByIdAndBotIdForUpdate()` pessimistic write lock;
- DISCOVERED -> NEGOTIATING requires exactly step 1;
- NEGOTIATING -> NEGOTIATING may keep the same step or advance by exactly one;
- a non-NEGOTIATING status update must preserve the existing step;
- negative steps and entering NEGOTIATING from unrelated statuses fail closed.

Verification:
- focused Mockito/JUnit 5 regression tests cover valid first offer, valid N->N+1, row-lock usage, step skipping, rollback, and terminal-status step rewriting.

Scope is backend-only and does not change selectors, browser behavior, target filtering, quota, or marketplace submit logic.
