## Description

## Problem
WorkerManager only scaled the worker pool upward. Once up to 10 slots had been started, reducing RUNNING bots to 3 left the old slots alive, which could keep their own Playwright/Chrome runtimes warm. This made scheduler Chrome count stay near the historical maximum instead of following the current RUNNING bot count.

## Fix
- reconcile slot capacity in both directions to `min(RUNNING bots, FLIPBOT_WORKER_COUNT)`
- surplus slots receive a graceful retirement request instead of `Future.cancel(true)`
- an idle retiring slot stops promptly; a slot already holding a claimed job finishes it first so scheduler state and real marketplace work are not interrupted
- BrowserManager is still closed by the worker itself on its owner thread
- preserve bounded headless browser reuse and the existing session persistence/checkpoint behavior
- add explicit target/active/retiring slot diagnostics

## Expected behavior
- 10 RUNNING bots with workerCount >= 10 -> target 10 scheduler slots
- 3 RUNNING bots -> target 3 scheduler slots; the other 7 retire after any already-claimed job finishes
- 0 RUNNING bots -> all scheduler slots retire and their browser runtimes are released
- an independent market-stats browser may still exist temporarily during a stats scan; it is not a scheduler worker slot

## Tests
- scaling plan regressions for 10->3, 3->10 and steady capacity
- idle BotWorkerSlot retirement test without launching Chrome
- full repository CI is the merge gate
