## Description

## Problem reproduced from runtime logs

The Observer itself was not failing, but it was far too slow to fill Price Matrix / market statistics:
- only 6 of 76 models were fully recorded in roughly 9 minutes,
- the first browser batch of 3 models took about 6 minutes,
- every newly discovered listing triggered a sequential detail-page visit just to obtain an exact publication timestamp,
- target ordering favored current RUNNING bot segments, so stale/unfinished models such as tablet/iPad rows could wait behind a large Samsung queue.

## Fix

### 1. Fast incremental publication path
Healthy incremental scans no longer open one Vinted detail page per newly discovered listing.

For a post-baseline incremental discovery:
- the scan remains complete without a detail-page timestamp lookup,
- backend persists firstSeenAt as the publication-time fallback,
- exact detail-page resolution is still mandatory for baseline recovery, incomplete publication windows, known rows missing a timestamp, and explicit full-catalog recovery.

This keeps historical recovery strict while making normal recurring scans much faster.

### 2. Fill unfinished/stale models first
Backend target ordering now prioritizes:
1. missing/incomplete baseline/publication coverage,
2. oldest last successful scan,
3. existing RUNNING-bot business priority,
4. stable brand/model ordering.

So rows that still show incomplete Observer coverage no longer sit behind every active Samsung model.

### 3. Freeze target order for a whole pass
Because scan-state freshness changes while a pass is running, Playwright now freezes the model order from the first batch and reuses it across browser recycling and retries. This prevents dynamic stale-first ordering from causing duplicate/skipped targets.

### 4. Reduce browser restart overhead
Default Observer browser recycle size increases from 3 to 6 model targets. It is still bounded/configurable and the same single headed/headless Observer browser is recycled; this does not increase Observer concurrency.

## Safety
- no changes to negotiation decisions, real-offer actions, quota/idempotency, or session persistence
- full/baseline historical reconstruction still requires exact Vinted publication timestamps
- healthy incremental fallback only applies to newly discovered post-baseline rows
- target order remains frozen during an in-progress pass so resume indexes remain correct
