## Description

## Co zmienia ten PR

Dodaje trwały runtime state dla schedulera oraz best-effort telemetry z modułu Playwright do backendu.

### Backend
- Flyway `V15__create_bot_runtime_state.sql`
- osobna tabela `bot_runtime_state` 1:1 z botem, `ON DELETE CASCADE`
- statusy: `IDLE`, `QUEUED`, `WORKING`, `COOLDOWN`, `ERROR`
- zapisuje:
  - `lastRunStartedAt`
  - `lastRunFinishedAt`
  - `nextRunAt`
  - `lastRunDurationMs`
  - `consecutiveFailures`
  - `lastError`
  - `workerSlot`
  - `updatedAt`
- `GET /api/bots/{botId}/runtime`
- `PATCH /api/bots/{botId}/runtime` dla zdarzeń schedulera
- rekord powstaje lazy przy pierwszym użyciu, więc istniejące boty nie wymagają backfillu

### Semantyka zdarzeń
- `QUEUED` -> oczekiwanie na normalny run + `nextRunAt`
- `RUN_STARTED` -> `WORKING`, zapis czasu startu i numeru slota
- `RUN_SUCCEEDED` -> zapis czasu/długości, reset `consecutiveFailures` i `lastError`
- `RUN_FAILED` -> `ERROR`, zwiększenie `consecutiveFailures`, zapis błędu i czasu retry
- `RATE_LIMITED` -> `COOLDOWN`, zapis czasu następnej próby bez traktowania rate limitu jako zwykłej awarii
- `IDLE` -> bot nie ma już zaplanowanego runa

### Playwright
- dodaje `RuntimeTelemetryClient` i asynchroniczny `RuntimeTelemetryReporter`
- telemetry działa na osobnym, pojedynczym wątku i nie blokuje locków schedulera ani worker slotów
- błąd telemetry jest best-effort: loguje warning, ale NIE przerywa pracy bota
- scheduler raportuje `QUEUED`/`IDLE`
- worker slot raportuje `RUN_STARTED`, sukces, błąd i rate limit
- po błędzie lub rate limicie job nadal siedzi w `DelayQueue`, ale runtime pozostaje odpowiednio `ERROR`/`COOLDOWN` aż do kolejnego `RUN_STARTED`
