## Description

### Fresh-log diagnosis
- Bot 3 / Galaxy S25 was **not** out of capacity: backend explicitly allowed 2 new negotiations and 79 candidates were eligible. The catalog run then spent ~3 minutes per candidate waiting on `HumanVerificationHandler` after the offer modal failed to open.
- The verification detector treated matching CAPTCHA/reCAPTCHA iframes in the DOM too broadly; hidden/background challenge widgets could stall a normal offer attempt.
- Bot 4 / Galaxy Tab S11 Ultra also had capacity (5) but repeatedly received 0 DISCOVERED listings from the backend after scanning 96 results.
- Backend marketplace `listingId` was globally UNIQUE and discovery de-duplicated IDs across every bot. That meant an item already seen by one bot could never be evaluated independently by another bot/configuration.
- Two legacy `/api/negotiations` endpoints also assumed marketplace listing IDs were globally unique and therefore had to become bot-scoped together with the data model.

### Changes
- require a challenge iframe to be visibly rendered at meaningful dimensions before pausing for human verification
- keep generic `Just a moment` / `Security check` markers title-only; visible body matching uses stronger human-verification phrases
- log the exact verification evidence when a real challenge is detected
- keep DOM/navigation read failures as inconclusive rather than CAPTCHA evidence
- scope marketplace listing identity to `(bot_id, listing_id)` in JPA and repository discovery
- add Flyway V29 migration that removes legacy global `listing_id` uniqueness and creates `uk_listing_bot_marketplace`
- make legacy negotiation result/offer-sent lookups explicitly require `botId + listingId`, preventing cross-bot ambiguity
- add regression tests for verification text strictness

### Expected behavior
- S25 catalog scans no longer freeze for 180 seconds merely because of a hidden challenge widget; a genuinely visible challenge still pauses safely for manual completion.
- Different bots may independently discover/evaluate the same marketplace item. A bot still processes its own marketplace listing ID only once, preserving its historical terminal state/backlog behavior.
- SEARCH_QUERY semantic filtering remains unchanged: S11 Ultra still rejects S10 FE+/wrong models/accessories.

### Safety
- no CAPTCHA is bypassed or automated
- no offer quota/action guard is weakened
- offer submission remains behind existing preflight, quota reservation and persistent real-action guards
- existing listing history is preserved; no rows are deleted by the migration
