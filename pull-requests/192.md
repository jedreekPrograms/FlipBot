## Description

## Problem
Multi-product listings already retain `additionalTargetId`, but the frontend drops it and history responses do not expose product provenance at all. This makes an ACTION_REQUIRED or historical listing ambiguous, especially when its additional product has since been disabled. Looking up only the current target label is also historically unsafe because product definitions can be edited later.

## Changes
- add nullable `listing.product_target_label` snapshot (Flyway V40)
- snapshot the MAIN/additional product label when a listing is first claimed
- refresh the snapshot only when a safe pre-negotiation listing is deliberately reassigned from a disabled target
- leave normal daily rediscovery and legacy rows untouched
- expose `additionalTargetId` + `productTargetLabel` in regular listing and history responses
- extend the Playwright listing DTO compatibly so the additional JSON field cannot break runtime deserialization
- show one consistent product label in Action Required and History:
  - `Produkt główny · <snapshot>`
  - `Dodatkowy #<id> · <snapshot>`
  - legacy rows fall back to `Produkt główny` / `Dodatkowy #<id>` without inventing historical data

## Safety
The snapshot is display-only. Runtime routing and negotiation strategy continue to use the stable `additionalTargetId` / target association; no real-action guard, quota, scheduler, or negotiation decision logic is changed.

## Tests
- main claim snapshots the MAIN product definition
- additional claim snapshots the additional product definition, not MAIN
- normal rediscovery preserves the original snapshot
- safe target reassignment replaces the snapshot with the new owner
- full repository CI is the merge gate

PR remains draft until all four CI jobs are green.
