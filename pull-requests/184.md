## Description

## Problem
Some low-volume Vinted targets do not justify a dedicated account/bot. Existing bots support one product configuration, so one Vinted account cannot safely scan and negotiate several independent products with different filters, price ranges and negotiation ladders.

## Changes
- keep every existing bot's current configuration as the unchanged main product
- add up to 4 optional additional products per bot (5 products total)
- persist separate category/brand/model/query, price range, adaptive offer settings and negotiation steps per additional product
- add frontend management for creating, editing, enabling/disabling and reviewing additional products
- keep the Vinted account, password, browser session and daily negotiation budget shared by the bot
- isolate discovered listing backlogs by product and persist the originating additional-target id on listings
- use the originating product's negotiation ladder for backend negotiation decisions
- scan active products sequentially in one authenticated Playwright session with rotating start order
- keep a shared per-run real-action cap across all products
- continue servicing conversations from disabled additional products with their original strategy
- preserve the old single-product runtime path when a bot has no additional products

## Isolation and safety
- discovery, backlog reads and negotiation capacity are explicitly product-scoped
- marketplace listing ownership cannot silently move between main/additional products
- active negotiations of an additional product do not unnecessarily lock structural edits of the main product
- shared Vinted account fields remain locked while any product has an active negotiation
- main-product config changes only requeue main-product listings; account-identity changes still requeue account-specific CANNOT_NEGOTIATE rows across all products
- shared daily budget is validated against every active product ladder
- additional-product rows use cascading foreign keys so deleting a stopped bot cannot be blocked by target-owned negotiation steps/listings
- schema initializer repairs pre-existing non-cascading additional-target foreign keys for local databases that already saw the feature branch

## Compatibility
Existing bots are not migrated into the additional-product table. Their current main product, credentials, sessions, listings and negotiation configuration remain in the existing schema. With zero additional products they continue through the original main-product endpoints and runtime behavior.

Inactive additional products are excluded from future catalog scans but stay in the Playwright payload so already-started conversations continue with the strategy that created them.
