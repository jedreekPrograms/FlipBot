## Description

## Problem
Runtime CAPTCHA recovery was incorrectly treating an authentication URL as a completed manual recovery before the CAPTCHA had actually been triggered.

Real logs show this sequence for bot 3:
- recovery opens `https://www.vinted.pl/member/login/email?ref_url=%2F` in headed Chromium
- no CAPTCHA is rendered yet because credentials have not been submitted
- `HumanVerificationHandler` reports that the challenge did not reappear
- recovery saves the session and closes the visible browser as if it succeeded
- the next headless login submits credentials and immediately hits DataDome again

## Fix
- detect Vinted `/member/login...` and `/member/register...` recovery URLs
- for those authentication challenges, replay the normal `LoginService` flow inside the visible browser instead of merely navigating to the pre-submit URL
- this causes the credential submit that originally triggered DataDome to happen in the headed recovery window, where the existing manual verification handling can actually wait for the user
- keep the existing direct challenge-page recovery path unchanged for non-auth CAPTCHA URLs
- add regression coverage for auth URL classification and trusted-host handling

## Expected flow
`CAPTCHA_REQUIRED -> Zaakceptuj CAPTCHA -> headed browser -> normal login flow -> credentials submitted -> real CAPTCHA appears -> user completes it -> session saved -> normal headless scheduling resumes`
