## Description

Stage 8 fixes one narrow real-action lifecycle bug in existing negotiations.

Finding:
- NEXT_STEP uses the persistent guard/quota/audit pipeline correctly, but ExistingNegotiationProcessor historically caught every Exception per listing and continued to the next conversation.
- If a real next-step submit became ambiguous after the click, or if the submit was confirmed but confirmed-audit persistence failed before the per-run sent counter was incremented, the same negotiation-check job could continue and attempt another real next step on another listing.
- The persistent guard still prevented retrying the same listing, so this was not a same-offer double-submit bug. The issue was continuing with another real action after a post-submit failure in the same job.

Fix:
- introduce a post-submit-only RealActionJobAbortException marker;
- ambiguous submits use AmbiguousRealActionException as its subtype;
- confirmed submit + confirmed-audit persistence failure also aborts the job while leaving the persistent guard fail-closed;
- ExistingNegotiationProcessor immediately rethrows this marker, so no other real next step is attempted in that run;
- ordinary inspection, target, availability and pre-submit failures keep the existing per-listing isolation and continue behavior.

First-offer flow was inspected and already propagates post-quota/post-submit failures out of the catalog job, so it is intentionally unchanged.

Scope is deliberately minimal: no selector changes, no target-flow changes, no quota/guard API changes, no database/backend/frontend changes. Includes a small regression test for the abort-marker hierarchy.
