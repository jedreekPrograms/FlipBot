## Description

## Problem

Fresh runtime logs show that exact category/brand/model filtering is working, but publication-time collection does not follow the intended Cennik flow. After a filtered catalog page loads dozens of listings, the current resolver only attempts at most three detail fallbacks per batch. Catalog hydration usually resolves 0 timestamps, so most listings never have their Vinted `Dodane ...` value inspected and the model remains incomplete.

Example from the latest run: a page loaded 54 matching listings, but detail fallback attempted only 3 and resolved 1/3. Model 68 later recorded 244 matched listings with `complete=false` because required publication timestamps were still missing.

## Changes

- Remove the three-listing detail fallback cap.
- Stop using background `fetch()` as the publication-time path.
- For every listing that still needs an exact publication timestamp, navigate the anonymous observer browser to the real Vinted item page sequentially.
- Read the visible `Dodane ...` value first; JSON-LD / hydrated `created_at_ts` are only same-page fallbacks after the item page has actually been opened.
- Pace item-page navigation and detect HTTP 403/429 / Vinted block pages using the existing traffic-backoff marker.
- Restore the exact filtered catalog URL after the required item details for that catalog page have been inspected, so normal pagination can continue.
- Keep already stored publication timestamps reusable because an item's publication time is immutable; new or previously unresolved listings are opened exactly once until resolved.

## Scope / safety

- No CAPTCHA or anti-bot bypass changes.
- Exact Vinted category/brand/model filter verification stays unchanged.
- OneTrust handling stays unchanged.
- No negotiation logic changes.
- Traffic remains sequential and paced; no parallel item requests.

## Tests

- The page extraction script reads visible `Dodane`, JSON-LD and same-page `created_at_ts`, and contains no `fetch()`/`Promise.all` shortcut.
- More than three unresolved listings are all selected for detail inspection.
- Known listings with stored publication time are reused, while missing/new listings are selected for item-page inspection.
