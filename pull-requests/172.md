## Description

## Problem
The publication-time observer now produces real calendar counts, but a model can still stay incomplete and undercount after migrating from the old baseline. Two things combine here:
- an incomplete retry can stop at the normal known-listing boundary before revisiting the rest of the filtered catalog,
- the exact hydrated `created_at_ts` resolver was previously removed because its JavaScript regex was broken by Java text-block escaping, leaving only rounded visible `Dodane ...` / JSON-LD fallbacks.

That matches the live symptom where e.g. `iPad 10.9 (2022)` shows fewer Today/This-week listings than a manual Vinted check and the UI says `Ostatni skan niepełny`.

## Changes
- expose per-model `full-catalog-scan-required` from backend scan state
- after an incomplete scan (or unfinished baseline), hide the known-listing early-stop boundary for the next observer retry so it traverses the full filtered catalog
- during that full retry, refresh publication timestamps for every visible accepted listing, not only new/missing rows
- once a complete pass is recorded, later scans return to the normal fast known-boundary behavior
- restore exact Vinted `created_at_ts` extraction from hydrated item data using index/string scanning only (no JavaScript regex)
- keep visible `Dodane ...` and JSON-LD as fallbacks
- retry unresolved item-detail fetches once with lower concurrency
- log resolved/unresolved publication timestamp batch counts and sample unresolved IDs

## Scope
Market-stats observer only. No changes to normal bot sessions, login/CAPTCHA, negotiations, quotas, or mobile connectivity.

## Tests
- backend tests cover when a full catalog retry is required
- observer context tests cover refreshing every visible known listing on a full retry
- resolver regression test keeps hydrated timestamp lookup regex-free
