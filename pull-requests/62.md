## Description

### Why
A listing can remain `DISCOVERED` because a previous catalog run hit negotiation capacity / `maxRealOffersPerRun` before reaching it. That listing must remain eligible in later runs instead of being starved forever by newer marketplace items.

The old `3 current-scan : 2 backlog` merge looked fair, but `NewNegotiationProcessor` may stop after the first 3 verified candidates. If those first 3 were always fresh, backlog candidates at positions 4-5 could still starve indefinitely.

### Changes
- distinguish **genuinely new this scan** listings from listings that were already persisted as `DISCOVERED`
- a previously DISCOVERED listing remains backlog even if it is still visible on page 1
- order the oldest backlog candidate first on every cycle
- after that, interleave `2 genuinely new : 1 backlog`
- keep old backlog ordered by backend id ascending (oldest first)
- keep genuinely new listings in Vinted newest-first order
- add regression tests for the exact scenario: yesterday's unstarted leftover + three new items today

### Intended contract
If yesterday 6 valid items appeared, the bot only had room to start some of them, and one valid listing stayed `DISCOVERED`, that listing remains eligible. When new items arrive tomorrow, the old unstarted listing gets a guaranteed chance in the next real-offer batch instead of being forgotten.

Only listings that actually transition out of `DISCOVERED` because of negotiation start or a real terminal reason (target mismatch, unavailable, outside price range, cannot negotiate, etc.) stop participating.

No quota, price, target, availability, CAPTCHA, or real-action safety guard is weakened.
