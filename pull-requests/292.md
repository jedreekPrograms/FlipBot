## Description

## Correct intended behavior

When Vinted still reports our latest offer as PENDING:

- seller formally rejects -> existing rejection policy
- seller reads the offer but leaves it PENDING -> use the SAME current-step rejection policy
- seller sends a normal chat message but leaves the offer PENDING -> use the SAME current-step rejection policy

There are no separate read/unread timers or extra bot configuration fields.

### WAIT_BEFORE_NEXT_STEP

If the current step says e.g. "wait 6h after rejection":

- formal rejection: wait 6h from first formal rejection detection
- read + PENDING: wait 6h from first read detection
- ordinary seller message + PENDING: wait 6h from first seller-message detection

The first detected seller reaction is persisted per step. Later reads/messages do not restart the timer.

### NEXT_STEP_NOW

If current-step rejection policy is immediate:

- formal rejection -> next step immediately
- read + PENDING -> next step immediately
- ordinary seller message + PENDING -> next step immediately

If there is no next step, PENDING seller reaction closes the conversation instead of inventing another price.

## No seller reaction

No-response handling remains bounded:
- WAIT rejection policy reuses its configured wait from step start
- immediate/legacy rejection policy uses the existing conservative 12h no-response fallback
- untouched final PENDING step retains the 48h final expiry

## Formal responses remain authoritative

ACCEPTED / formal SELLER_COUNTER_OFFER / formal REJECTED / CANCELLED continue through their existing formal-response paths. Read/chat policy is used only when the latest Vinted offer state is still PENDING.

## Robustness fixes

- ordinary seller message without a usable Vinted timestamp now persists the first detection time instead of having no stable timer
- a stale/imprecise Vinted message timestamp is normalized to detection time when the DOM proves the message is after our latest offer
- backend preserves the first seller-activity timestamp for the current step; later chat messages cannot restart the wait
- current-step activity clocks are still reset when a new negotiation step starts
- UI explicitly explains that the "after rejection" rule is also reused for read/chat while the offer remains PENDING

## Price handling

No real seller price is special-cased in runtime logic. Existing regression examples were renamed/replaced with generic test values.

## Existing safeguards unchanged

- hard 25/day quota
- persistent action/idempotency guard
- adaptive global cap
- strategy snapshots/versioning
- terminal recovery watcher
- Vinted live-minimum handling
- formal seller counteroffer <= configured cap -> ACTION_REQUIRED
