## Description

## Problem
Worker slots intentionally reuse one Playwright `BrowserManager` for throughput. Slot threads stay alive even when the number of RUNNING bots later drops, so every slot that handled work earlier can keep a Chrome runtime/process group alive for the rest of the process lifetime.

That can accumulate many Chrome groups in Windows Task Manager. In headful mode it can also leave many visible idle windows. This is separate from bot-session persistence: authentication is stored in validated `sessions/bot-X.json` storage-state snapshots, not in the lifetime of the Chromium process.

## Changes
- keep worker slot/thread scheduling semantics unchanged
- headful workers release their `BrowserManager` after every completed/failed/rate-limited/session-blocked job
- headless workers may reuse Chromium between nearby jobs for throughput, but only while useful
- add a timed scheduler poll so a headless worker wakes even when no task becomes ready
- after `FLIPBOT_BROWSER_IDLE_TIMEOUT_SECONDS` without a ready job, release the idle headless Chromium runtime and continue waiting without Chrome
- default idle timeout is 180 seconds (allowed 30..3600), deliberately longer than the default 120-second negotiation-check interval so active negotiation workers remain warm
- release an already-open browser immediately when a claimed task is deferred by a persisted session cooldown
- launch a fresh runtime lazily when the slot later receives work
- perform all browser close operations on the owning worker thread
- cleanup remains in `finally`, including when rescheduling fails

## Session safety
No changes to `SessionManager`, login logic, authenticated pre-job checkpointing, final healthy-session validation, last-known-good rollback, storage-state format, or `ScheduledBotRunExecutor` save order.

Each scheduled job still:
1. restores the bot's validated storage state into a fresh per-job `BrowserContext`,
2. authenticates/verifies the session,
3. checkpoints the authenticated state,
4. runs the job,
5. saves only a healthy successful final state,
6. closes the per-job context,
7. only then returns control to worker-level browser retention/cleanup.

Closing the outer Chromium runtime therefore does not delete or recreate the saved bot session.

## Tests
- headless post-job policy retains the same browser reference without closing it
- headful post-job policy invokes close exactly once and drops the reference
- missing runtime does not invoke close
- timed scheduler polling returns a ready current task
- timed scheduler polling returns `null` while all scheduled work remains in the future, giving the worker its idle-cleanup boundary
- full repository CI is the merge gate

PR remains draft until the latest head passes all CI jobs.
