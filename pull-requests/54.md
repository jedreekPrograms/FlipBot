## Description

## Why
The latest runtime log exposed three separate issues that made historical offers hard to reason about:

1. `VINTED_MODEL` exact matching used `Pattern.UNICODE_CASE`, which Playwright Java cannot serialize to its JS regexp flags. This caused the Galaxy S25 catalog scan to fail while selecting the exact model.
2. A valid historical Galaxy Tab S11 Ultra listing was permanently marked `SKIPPED_CANNOT_NEGOTIATE` after a single 15-second wait for the first-offer action. That is too aggressive: a delayed Vinted render is not proof of blocking or a permanent seller restriction.
3. Negotiation capacity was correct after PR #52, but the runtime only printed `may start 0`, so it was impossible to see which active conversations were reserving future steps and how the daily quota contributed.

## Changes
- Fix exact Vinted model filtering to use only the Playwright-supported `CASE_INSENSITIVE` regexp flag while preserving exact-match behavior (`Galaxy S25` does not match Edge/Ultra/FE/+).
- Add a regression test that asserts the exact-model regexp uses only the supported flag.
- When a fully loaded item page has no first-offer action, require **3 independent observations** before returning `CANNOT_NEGOTIATE`. Each observation already waits up to 15 seconds; between observations the item page is reloaded and allowed to settle. A single missing button no longer permanently skips a valid historical candidate.
- Make logs explicit that repeated missing offer action does **not** prove the seller blocked the account; it only confirms that Vinted repeatedly exposed no negotiation action to this account.
- Add Flyway `V28__requeue_legacy_cannot_negotiate_listings.sql` to move old step-0 `SKIPPED_CANNOT_NEGOTIATE` listings back to `DISCOVERED`, so listings skipped under the old one-shot detector receive one safe retry under the stronger detector.
- Add detailed backend capacity diagnostics showing daily limit/used/remaining, every active `NEGOTIATING`/`ACTION_REQUIRED` listing and its reserved future actions, total reservations, actions left after reservations, and resulting full-conversation capacity.

## Capacity semantics
No reservation semantics are changed. The planner still follows the intended model:
- today's actually sent actions consume today's quota;
- every active conversation reserves `maxSteps - currentStep` future actions;
- a new conversation needs room for its full configured ladder;
- old active conversations keep their future reservations across midnight.

## Runtime impact
No new environment variables. Backend must restart first so V28 can requeue old one-shot `SKIPPED_CANNOT_NEGOTIATE` decisions, then Playwright must restart for the stronger first-offer check and S25 model-filter fix.
