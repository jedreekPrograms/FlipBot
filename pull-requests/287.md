## Description

## Root cause

Runtime logs from the current `main` showed that reactive memory downscaling still happened too late on process start:

- 10 RUNNING bots immediately claimed 10 NEGOTIATION_CHECK jobs.
- all 10 worker slots created Chromium runtimes before the next memory samples could react.
- the adaptive target then dropped 10 -> 8 -> 6 -> 4, but in-flight jobs are intentionally not killed, so `working=10` remained for several minutes.
- physical memory reached 99% used with only ~0.3-0.5 GiB free while the Observer was scanning.

This also made Observer category navigation slow/retry-heavy and stretched the first 3-model batch to roughly six minutes.

## Fix

- start adaptive worker capacity with a conservative cold-start cap of 4 slots
- preserve the existing safe recovery behavior: add only one slot after the RAM level stays healthy for the recovery hold window
- preserve all existing elevated/high/emergency pressure caps
- disabled adaptive-memory mode still gets the configured parallelism immediately
- smaller requested capacity is still respected

## Why this is safer

Downscaling cannot safely interrupt an in-flight marketplace action. Preventing the launch storm before jobs claim work is therefore safer than trying to kill Chromium after RAM is already exhausted.

## Safety

No negotiation decisions, offer submission, 25/day quota, session persistence, Observer filtering, Price Matrix calculations, or analytics semantics are changed.
