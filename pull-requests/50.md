## Description

## Problem
The S11 Ultra runtime log repeatedly opened the same conversation, decided that step 3 should be sent, reached `Conversation is ready`, then failed before `Chat offer button found`. The same negotiation was retried every 2 minutes.

One plausible real-world cause is that contact with the seller is no longer possible (for example one member blocked the other). We should not treat a read-only conversation as a generic transient UI failure forever, but we also must not label every missing offer button as a block.

## Fix
- add conversation contact/action-availability inspection immediately before a next-step action
- distinguish four states:
  - `AVAILABLE`: enabled `make-offer-request-button` is present -> normal next-step flow continues
  - `OFFER_ACTION_UNAVAILABLE`: message composer is still visible+enabled, but offer action is unavailable -> do not classify as blocked; skip the offer safely and retry on a later check without quota/guard/generic timeout
  - `SUSPECTED_UNAVAILABLE`: neither a usable composer nor an enabled offer action appears after 5 seconds -> do not send; require repeated confirmation
  - `CONFIRMED_UNAVAILABLE`: Vinted explicitly reports contact disabled/blocked, or an `Unblock` action is exposed -> stop immediately
- require 3 consecutive `SUSPECTED_UNAVAILABLE` checks before closing, so one slow/transient render cannot permanently kill a negotiation
- reset the suspicion counter as soon as usable interaction returns
- add terminal `CONTACT_UNAVAILABLE` listing status and Flyway V26 constraint update
- preserve conversation id/current step/current price when moving to `CONTACT_UNAVAILABLE`

## Important safety detail
A usable message composer without a negotiation button is deliberately **not** treated as a block. This may simply mean Vinted does not currently allow another price offer in that conversation. The bot logs this separately and retries later instead of making a false permanent classification.

## What is intentionally unchanged
- PENDING/read/normal-message policy remains unchanged:
  - seller normal message -> wait 3h, then next step if available
  - read indicator -> wait 3h, then next step if available
  - no engagement -> expire after 48h
- formal rejection/counteroffer response policies remain unchanged
- quota, persistent action guard, production gating and adaptive pricing remain unchanged

## Tests
- enabled offer action => AVAILABLE
- enabled message composer without offer action => OFFER_ACTION_UNAVAILABLE, not blocked
- disabled/missing interaction controls => SUSPECTED_UNAVAILABLE
- explicit blocked/contact-disabled signal => CONFIRMED_UNAVAILABLE
- only the 3rd consecutive suspected observation becomes terminal
- successful contact observation resets the suspicion counter
- counters remain isolated per bot/listing
